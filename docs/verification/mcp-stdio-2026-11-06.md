# MCP stdio lifecycle verification — 2026-11-06

This verifies development transport/lifecycle behavior. It is not a release,
image promotion or complete SOLIDWORKS functional acceptance. Existing CAD
handlers, protocol schemas, COM worker and native/group timeouts are unchanged.
The MCP adapter and CLI opt-in use a shared client startup path.

## Portable and packaging checks

- Official MCP Python SDK **1.30.0**, real stdio subprocess initialize/list/ping,
  selected capability queries, successful execution, native failure `isError`,
  invalid-argument refusal and EOF without sending daemon shutdown.
- Two official-SDK MCP subprocesses share one mock protocol daemon with distinct
  default sessions; closing one leaves the other usable.
- MCP regressions cover stable request IDs, zero CAS stamps, native lease refusal,
  loss-of-reply unknown outcome, no native retry, existing-host failure, lazy
  first-use startup once, remote/connect-only behavior and literal path mapping.
- CLI `--auto-start` is explicit and only affects typed CAD commands; version,
  schema, status and capability discovery do not launch a host.
- Optional SDK imports remain lazy, Python 3.9 base CLI remains supported; the
  modern Windows CI unit job installs the MCP extra and exercises interoperability.
- Full portable regression and final affected tests passed. Wheel/sdist build,
  Twine strict, sdist contents, isolated installed schemas/skill and skill
  validation passed; workflow syntax passed actionlint.

## First failures and targeted corrections

The first native run successfully started/queried SW, but after MCP shutdown
the Windows SDK's kill-on-close Job Object also killed the descendant daemon;
SW remained outside that job. This was a real lifecycle failure, not accepted
as success. The empty owned test host was identity-checked and explicitly cleaned.

For clients in a Windows job, a demand-only, same-user, non-elevated Task
Scheduler action now runs the existing foreground daemon outside that client
job. It uses the exact interactive session, no password and no boot/logon
trigger; its unique task definition is deleted after startup. Ordinary launches
outside a client job use the existing start_daemon path. SW COM remains wholly
inside the existing worker.

A platform-only parameter failure was narrowed to `Task.RunEx` receiving
VT_NULL: explicit empty BSTR values fixed it, and the minimal non-CAD task
probe passed. The next startup identified invalid task console handles in the
bootstrap's low-level dup2 redirection. Replacing only Python stdout/stderr
with a UTF-8 log stream fixed this; an absent-console-stream regression passed.
Only then was a new native lifecycle probe run and accepted. Earlier original
reports and hashes are preserved in the adjacent JSON and Windows workspace.
No failed CAD API was retried, limits were not relaxed, and no native rollback
or in-group restart was introduced.

The independent-visible-plus-hidden instance experiment is separate and did
not pass both-host acceptance; see
[multi-instance diagnostics](mcp-instance-isolation-2026-11-06.md). This feature
does not enable that default or change attach ownership.
