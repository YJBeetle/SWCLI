# SWCLI 0.2.3

- The existing daemon endpoint supports certificate-verified TLS 1.2 or newer
  and token-file authentication. Clients verify the certificate chain and
  hostname; authentication completes before CAD requests are submitted, with
  no plaintext fallback. Windows startup tasks propagate configuration paths
  and flags without putting token contents into command lines or RPC requests.
- `swcli transfer upload` and `download` stream files between explicitly
  configured client and daemon workspaces. Transfers use 1 MiB chunks, a
  default 1 GiB per-file maximum, size/SHA256 verification and atomic
  destination publication. Existing destinations require explicit overwrite.
- Workspace paths reject parent traversal, device names, alternate data streams,
  symlinks, Windows junctions/reparse points and hard-linked inputs. Active
  transfers, cached receipts and idle lifetime are bounded. Interrupted uploads
  can be resumed explicitly in the same session; CAD operations are not retried.
- Configuring a client workspace adds MCP `upload_file` and `download_file`
  tools with byte progress. Large downloads are saved in the MCP server's
  client workspace; they are not embedded as unlimited chat attachments.
  Existing render/export attachments retain their 8 MiB limit.
- CLI, MCP and packaged skills share the connection and transfer configuration.
  Local connections and explicit daemon/SW lifecycle protections remain intact.

Use SWCLI 0.2.3 or newer at both ends for these features. The shared token grants
access to the daemon account's operations; it is not multi-user role-based
access control. Protect key/token files and restrict reachable hosts. See the
packaged remote/workspace guide for separate host paths and recovery limits.

The version-tag workflow runs complete installed Windows verification before
publishing the original same-run packages. DockerSW and MacSW releases remain
independent.
